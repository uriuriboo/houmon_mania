## 0. 本書の位置づけ

本書は要件定義のみを対象とする。以下は本書の範囲外とし、別文書(基本設計書・詳細設計書)で扱う:

- 画面遷移・UI具体仕様
- 内部設計(ワーカーの分担、シーケンス図等)
- 保存データの物理設計確定(型・インデックス・項目の最終値)
- 配信構成・デプロイ手順の詳細

本書に含まれるデータ定義・技術スタック等は「要件を満たすための想定」であり、基本設計時に変更されうる。

### 0.1 変更の経緯

1. **API 方式をやめた理由**: Foursquare の Personalization API の利用ガイドライン(2026-02-12 更新)が、一般の開発者に対して ID 以外のデータのサーバー保存を禁止している。チェックインを同期・保存して検索する当初の方式は、この規定と衝突する(技術調査報告書 2.1)。
2. **公式エクスポートを使う理由**: 利用者は Foursquare 公式の「Download your data」で、自分のデータを ZIP で受け取れる。これを使えば Foursquare API を一切呼ばずに済む。
3. **サーバーに保存しない理由**: 自分のデータを自分で検索する用途なら、データを利用者の端末(ブラウザ)の中に置けば足りる。運営者はチェックインも位置情報もメールアドレスも預からず、ログイン・データベース・個人情報の管理がまるごと不要になる。

### 0.2 方式変更の影響

| 区分 | 内容 |
|---|---|
| 規約・プライバシー | 運営者は Foursquare 由来のデータも個人情報も預からない。データは利用者の端末から出ない(写真の表示で Foursquare の画像サーバーに接続することを除く) |
| 検索できる項目 | **エクスポートのチェックインには住所・市区町村・カテゴリが含まれない**ため、検索対象は「店名・コメント(shout)」(と、場所名・イベント名)になる。例: `カフェ` でスターバックスは見つからない、`渋谷` は店名に「渋谷」が入っている店だけ見つかる |
| 鮮度 | 自動同期は無い。新しいチェックインを反映するには、利用者が再申請し(通常2〜3日、最大7日)、ZIP を読み込み直す |
| 端末ごとの利用 | データはブラウザごとに別。PC とスマホの両方で使うなら、それぞれで読み込む |
| データが消える可能性 | ブラウザのデータを消すと消える。Safari は7日間サイトを開かないと消えることがある(ホーム画面に追加すれば避けられる)。消えても ZIP を読み込み直せば戻る |
| 共有端末 | ログインが無いので、同じブラウザを使う人は誰でもデータを見られる。共有端末では使わないよう案内し、すぐに消せるようにする |

## 1. 概要

| 項目 | 内容 |
|---|---|
| 目的 | 利用者が Foursquare 公式のデータエクスポートをブラウザで読み込み、チェックイン履歴を店名・コメントのキーワードで AND/OR 検索(入れ子構造含む)できる Web アプリ。データは利用者の端末の外に出さない |
| 想定利用者 | 不特定多数への一般公開。各自が自分のデータエクスポートを、自分の端末で読み込んで使う。非商用で、本人のデータを本人が検索する用途に限る |
| プラットフォーム | Webアプリ(レスポンシブ)。静的な Web アプリで、サーバー側の処理は持たない |

## 2. スコープ

### 2.1 MVPに含むもの
- エクスポート ZIP の読み込みとブラウザ内への保存
- キーワードによるAND/OR検索(入れ子構造対応、liqeによるクエリパース、ブラウザ内で照合)
- 検索結果一覧・詳細表示(保存データのみ)
- 保存データの削除
- ローカル開発環境の整備

### 2.2 MVPに含まないもの(将来検討)
- 地図上での可視化
- 他ユーザーとのチェックイン共有・比較
- liqeのフィールド指定構文(`venue:xxx`等)・範囲検索などの高度な機能(パース結果に含まれても未対応入力としてエラーにする)
- モバイルネイティブアプリ
- Foursquare API の利用(同期・詳細取得・住所やカテゴリの補完)
- ログインとサーバーへの保存、端末間の同期
- 写真ファイルの取り込み(写真は画像 URL で表示する)

## 3. 機能要件

要件IDは、方式変更前の番号を引き継いでいる。削除した要件の番号は詰めずに欠番とする(欠番: F-01、F-02、F-05、F-15、F-41、F-42、L-03、L-04、L-06、N-02、N-03、N-04、N-07、N-08、N-09)。

### 3.1 データの管理

| ID | 要件 |
|---|---|
| F-03 | 利用者は、このブラウザに保存したデータをすべて、いつでも即時に削除できる |
| F-04 | データ管理画面で、保存件数、保存済みの最新チェックインの日時、最終取り込み日時、保存領域の状態(永続化されているか、使用量)を確認できる |

### 3.2 データ取り込み

| ID | 要件 |
|---|---|
| F-10 | 利用者は Foursquare 公式のデータエクスポート(ZIP)を選んで、全履歴を取り込める。ZIP の展開と必要なファイル(チェックインと写真の情報)の抽出はブラウザの中で行い、どのデータもサーバーに送らない |
| F-11 | 取り込み中は進捗(読み込み・保存の件数)を表示する |
| F-12 | 新しいエクスポートを再度読み込むと、差分(新規・変更・削除)を反映する。チェックインIDをキーに冪等に取り込む。削除の反映は、完全なエクスポートを読み込み、利用者が削除件数を確認した場合に限る |
| F-13 | チェックインレコードから保存してよい項目だけを取り出して raw として保存し、検索・表示に使う項目は個別にも持つ |
| F-14 | 取り込みに失敗した場合(形式の不一致、保存領域の不足など)は、原因と対処を表示し、やり直せる(冪等なので、最初からやり直しても重複しない) |
| F-16 | エクスポートの申請手順(Swarm アプリ・Web の操作手順、届くまでの目安)を画面で案内する |
| F-17 | 保存データが消えにくいよう、ブラウザに保存領域の永続化を要求し、その結果を表示する。消えた場合は再取り込みを案内する |

### 3.3 検索

| ID | 要件 |
|---|---|
| F-20 | ユーザーはキーワードとAND/OR演算子、括弧による入れ子構造(例:`A OR (B AND C)`)を用いて検索できる。AND と OR を括弧なしで混在させた検索式と、小文字の and / or はエラーにする(基本設計書 17章 D-4・D-5 で決定) |
| F-21 | 検索クエリはliqeでパースし、AND/OR/括弧の構造に変換して、ブラウザの中で保存データと照合する |
| F-22 | 検索対象:店名・コメント(shout)・場所名(店の無いチェックイン)・イベント名。住所とカテゴリはエクスポートに含まれないため対象外 |
| F-23 | 全角/半角・大文字/小文字の表記ゆれを吸収する(NFKC正規化。データと検索語の両方に同じ正規化をかける) |
| F-24 | 検索結果は日時降順、ページネーションあり |
| F-25 | 検索処理自体は外部へアクセスしない(保存済みデータのみを検索) |
| F-26 | liqeのフィールド指定・範囲検索等、AND/OR/括弧以外の構文が入力された場合はエラーメッセージを返す(未対応構文として明示的に弾く) |

### 3.4 表示

| ID | 要件 |
|---|---|
| F-30 | チェックイン一覧:日時・店名・コメント・写真枚数・公開範囲(カテゴリはエクスポートに含まれないため除く) |
| F-31 | 検索結果件数の表示、該当なし時の表示 |
| F-33 | 詳細は保存データのみで表示する。写真は、エクスポートの写真情報にある画像 URL で表示する。Foursquare の店ページへのリンクを付ける |

### 3.5 データ保持・削除

| ID | 要件 |
|---|---|
| F-40 | 利用者の削除操作で、保存データを即時に削除する。猶予期間は設けない(基本設計書 17章 D-2 で決定) |

### 3.6 ローカル開発環境

| ID | 要件 |
|---|---|
| L-01 | `next dev` だけでローカル開発できる(Docker・Supabase は不要) |
| L-02 | ブラウザ内の保存形式(IndexedDB のスキーマ)に版番号を付け、版の移行処理をコードで管理する |
| L-05 | 架空のデータから生成した疑似エクスポートを fixture として用意し、取り込みと検索のテストに使う。実物から作る場合は形式の確認に必要な最小限の件数とし、個人を特定できる値をすべて架空の値に置き換える。実物の ZIP・JSON はリポジトリに入れない |

## 4. 非機能要件

| ID | 要件 |
|---|---|
| N-01 | データは利用者のブラウザの中だけにあり、他の利用者や運営者からは見えない。同じブラウザを使う人からは見えるため、共有端末での利用を避けるよう案内する |
| N-05 | 数万件規模でも検索応答が数百ms程度に収まる(ブラウザの中で、一般的なスマホでも5万件で数百ms以内) |
| N-06 | エクスポートの形式が変わっても、取り込み済みのデータは影響を受けない(rawの保持による担保)。新しい形式には取り込み処理の改修で対応する |
| N-10 | SQLを使わない。検索式は構造に変換してから照合し、文字列として評価・実行しない |
| N-11 | 取り込んだデータは、利用者の端末の外に送らない。不要な情報(友人一覧、支払い・端末情報など)は読み込まない |
| N-12 | 1回に取り込める件数・ファイルの大きさに上限を設け、端末が固まらないようにする |
| N-13 | 取り込んだデータがスクリプトで外部に送られないよう、外部への通信先を制限する(CSP) |

## 5. データモデル(想定・基本設計で確定)

データは利用者のブラウザの IndexedDB に保存する。サーバー側のデータベースは持たない。

| ストア | 内容 |
|---|---|
| `checkins` | チェックイン。id(キー)、created_at、tz_offset、shout、venue_id、venue_name、location_name、lat、lng(含まれている場合のみ)、event_name、photo_count、raw(許可した項目だけで組み立て直したレコード) など。address・city・state・country・categories は持たない |
| `search_index` | 検索と差分の算出に使う最小限の値(id、created_at、検索用の正規化テキスト、内容のハッシュ) |
| `photos` | 写真の情報(photo_id、checkin_id、画像 URL の組み立てに使う prefix・suffix など) |
| `meta` | 取り込み状況、保存形式の版など |

## 6. 取り込むエクスポートの形式(想定・実物で確認して確定)

Foursquare はエクスポートの形式を公式に文書化していない。次は実例から組み立てた想定で、実物で確認して確定する(着手事項 S-1)。

| ファイル | 想定 |
|---|---|
| `checkins*.json` | `{"count": N, "items": [チェックインレコード…]}`。1000件ずつ分割。id、createdAt、type、visibility、timeZoneOffset、shout(任意)、venue({id, name, url} のみ)、comments(件数)など |
| `photos*.json` | 写真の情報(id、createdAt、prefix、suffix、width、height、visibility、relatedItemUrl など)。relatedItemUrl の末尾がチェックインID |
| その他(友人一覧、訪問履歴、支払い・端末情報、写真の実ファイルなど) | 読み込まない |

## 7. 技術スタック(想定・基本設計で確定)

| 領域 | 選定 |
|---|---|
| フロントエンド | Next.js(静的書き出し)+ TypeScript |
| ホスティング | Netlify(静的配信のみ。サーバー側の処理は使わない) |
| 保存 | ブラウザの IndexedDB |
| 検索クエリパース | liqe(AND/OR/括弧のパース、フィールド構文等は未対応入力として弾く) |
| 検索 | liqeの結果を構造に変換し、ブラウザ内で正規化済みの文字列と部分一致で照合 |
| ローカル開発 | `next dev` |

## 着手事項(実物での確認)

実物の確認が必要な検証の一覧。詳細設計と並行して行い、結果を詳細設計に反映する。当初の着手事項のうち、API・Supabase に関する検証は不要になった(番号の混乱を避けるため、欠番として振り直さない: S-2、S-3)。liqe のパース検証は実施済み(技術調査報告書 9章)。

| ID | 内容 |
|---|---|
| S-1 | **実際の2026年版エクスポートを取得し、形式を確かめる(最優先)**。ファイル名と分割、チェックインの項目(特に座標の有無)、日時の形式、写真の URL の表示可否など |
| S-4 | Netlify への静的サイトのデプロイ(CSP などのヘッダ) |
| S-5 | ブラウザでの ZIP の読み込みと取り込み時間・メモリ(PC・スマホ) |
| S-6 | ブラウザ内での検索の速さとメモリ(PC・スマホ、5万件・20万件) |
| S-7 | 保存領域の永続化と、データが消える条件(iOS Safari・Android Chrome・PC) |
