## 9.1 保存領域と起動

### 9.1.1 保存先【決定】

- IndexedDB に保存する。localStorage は容量が小さく(数MB)同期処理で画面を止めるため使わない。
- IndexedDB の操作には薄いラッパーライブラリを使う(候補は詳細設計で比較する)。
- 保存領域はオリジン(ドメイン)ごと・ブラウザごとに別。同じ端末でも、ブラウザが違えば別のデータになる。
- プライベートブラウズでは、ウィンドウを閉じると消える。ブラウザからはプライベートブラウズかどうかを確実には判別できないため、取り込み画面に常に注意書きを表示する。IndexedDB を開けない場合は、エラー画面(SCR-E)で「保存領域が使えない」ことと対処を示す。

### 9.1.2 データが消えにくくする工夫(F-17)【暫定 S-7】

| 対策 | 内容 |
|---|---|
| 永続化の要求 | 初回の取り込みが完了したら `navigator.storage.persist()` を呼ぶ。結果をデータ管理画面に表示し、未許可なら「許可を求める」ボタンから再度求められるようにする。対応していないブラウザでは「不明」と表示する |
| ブラウザごとの違い | Chrome・Edge は利用者に確認せず、利用状況(ブックマーク、ホーム画面への追加、よく使うサイトか)から自動で判断するため、始めは未許可になることが多い。**未許可でも異常ではない**と表示する。Firefox は確認を表示するため、利用者の操作(ボタン)から呼ぶ |
| ホーム画面への追加 | Web アプリのマニフェストを用意し、ホーム画面に追加できるようにする。iOS の Safari は、7日間サイトを使わないとサイトのデータを消すことがあるが、ホーム画面に追加した Web アプリはこの対象外とされる。**ただし、Safari とホーム画面のアプリは保存領域が別**で、Safari で取り込んだデータはホーム画面のアプリからは見えない。そのため iPhone・iPad では、トップと取り込み画面で、**取り込みの前に**ホーム画面に追加し、ホーム画面のアイコンから開いて取り込むよう案内する【提案】 |
| 使用量の表示 | `navigator.storage.estimate()` で使用量を表示する |
| 消えたときの案内 | データが無い状態では、消えた可能性と対策、読み込み直せば戻ることを案内する |

### 9.1.3 保存形式の版と移行

- 保存形式に版番号を付ける(`meta.schema_version`、IndexedDB のデータベースの版)。
- 抽出項目を増やすなど形式を変えたときは、起動時に移行処理を行う。保存済みの raw から値を作り直せる場合はそうし、作り直せない場合は再取り込みを案内する(N-06)。
- 移行は取り込みワーカーが、取り込み・削除と同じ排他ロックを取って行う。移行中は「データを更新しています」と表示する。
- 新しい版でデータベースを開くと、古い版で開いている他のタブに `versionchange` が届く。受け取ったタブは接続を閉じ、「新しい版があります。再読み込みしてください」と表示する。
- 他のタブが接続を閉じず、開き直しが保留(blocked)になった場合は、「他のタブを閉じるか再読み込みしてください」と表示し、閉じられたら続ける。

### 9.1.4 起動時の確認(APP-01)

4.2.1 のとおり。保存データの有無、保存形式の版、取り込み中の印(前回の取り込みが途中で終わっていないか)を確認してから、検索ワーカーに準備を依頼する。

戻る/進むでページがキャッシュ(bfcache)から復帰したときは、離れている間に他のタブで取り込みや削除が行われている可能性があるため、`pageshow` で同じ確認をやり直す。

## 9.2 取り込み方式

### 9.2.1 全体の流れ【決定】

1. 利用者が Foursquare にエクスポートを申請する(本アプリは手順を案内するだけ。IMPT-01)。
2. 届いた ZIP(または展開済みのフォルダ)を利用者が選ぶ。
3. 取り込みワーカーが排他ロックを取り、ZIP の目次だけを読み、`checkins*.json` と `photos*.json` だけを展開する(写真の実ファイルを含む大きな ZIP でも、全体をメモリに読み込まない)。
4. ワーカーが検証・組み立て直し・差分の算出を行い、**保存する前に**結果を画面に表示する。
5. 利用者が「取り込む」を押すと、ワーカーが一定件数ずつ保存する。削除候補は、安全条件を満たし、利用者が反映を選んだ場合だけ削除する。
6. 完了したら取り込み状況を更新し、排他ロックを解放し、他のタブに知らせ、初回なら永続化を求める。

排他ロックは、分析の開始から保存の完了(または中止)まで保持する。分析と保存の間に別のタブが保存すると、算出した差分が古くなるためである。別のタブで取り込み・削除・移行の実行中は、取り込みを始められない。

取り込みの間は、対応するブラウザでは Screen Wake Lock で画面のスリープを防ぐ(Permissions-Policy で無効にしない。10.2)。スマホでは他のアプリに切り替えるとワーカーが止まることがあるため、「終わるまでこの画面を開いたままにしてください」と表示する。

### 9.2.2 ファイルの読み込み(IMPT-02)

選べるもの:

| 選び方 | 内容 | 削除候補の反映 |
|---|---|---|
| ZIP | 届いたエクスポートの ZIP をそのまま選ぶ(標準) | 可(9.2.4 の条件を満たす場合) |
| 展開済みのフォルダ | macOS の Safari などが ZIP を自動で展開した場合に、フォルダごと選ぶ。フォルダの中から `checkins*.json` と `photos*.json` だけを読み、他のファイルは開かない | 可(ZIP と同じくファイルの欠けを確かめられるため) |
| JSON ファイル | `checkins*.json` と `photos*.json` を直接選ぶ | 不可(エクスポート全体がそろっているか確かめられないため) |

ZIP の展開に使うライブラリの条件(候補は詳細設計で比較する):

- ファイルを `Blob.slice` で部分的に読み、ZIP の目次から必要なファイルだけを展開できる(ZIP 全体をメモリに読み込まない)。
- ZIP64(4GB を超える ZIP、65,535 を超えるファイル数)を読める。写真を含むエクスポートは大きくなりうるため。
- 展開をストリームで行い、**実際に展開したバイト数**で上限を判定して途中で止められる(目次に書かれた大きさは信用しない)。
- ライブラリが内部で Blob URL のワーカーなどを作らない(CSP の `worker-src 'self'` で動く。10.2)。

大きさの上限(N-12。値は詳細設計で決める):

- ZIP の目次のファイル数の上限(目次が異常に大きい ZIP を止める)。
- 展開後のファイル1つあたりの大きさ。分割されていない古い形式の `checkins.json` は別の上限にする(S-5)。
- 展開するファイルの合計の大きさ、チェックインの総件数(20万件)。

超える場合は止める(圧縮爆弾などで端末が固まるのを防ぐ)。

読み込み時の検証: 必要なファイルがあるか、`checkins` の連番に欠番が無いか、各ファイルの `count` と `items` の件数が一致するか、同じ名前のファイルが複数のフォルダに無いか(複数のエクスポートが混ざっていればエラー。7.1)。

### 9.2.3 検証と組み立て直し

- 各レコードを zod で検証する。zod は CSP の `unsafe-eval` を許可しないで動かすため、`z.config({ jitless: true })` を設定する(10.2)。
- **raw は、許可した項目(id、createdAt、type、visibility、private、shout、timeZoneOffset、venue の id・name・url、location の name・lat・lng、event の id・name、comments の count)だけで組み立て直す**。未知の項目は保存しない(形式変更の検知のため、項目名だけを分析結果の警告に含める)。
- 値の範囲(日時、タイムゾーン、緯度経度)と文字列の長さを検証し、raw は1件 16KB 以下(UTF-8 のバイト数)とする。
- ID は正しいが内容が不正なレコードは保存しないが、「エクスポートに含まれていた」ものとして扱い、削除候補にはしない。
- 同じ ID のレコードが複数あれば1件にまとめる。
- 検索用テキストと内容のハッシュを作る(9.3.3、6.2)。写真の情報をチェックインに対応付け、URL のパターンを検証する(9.4)。
- 取り込み状況に記録するファイル名は、パターン(`checkins*.json`、`photos*.json`)に一致したものだけとし、長さに上限を設ける。

### 9.2.4 差分と削除の安全条件(IMPT-02・03)

保存済みのデータ(`search_index` の ID と内容のハッシュ)と比べて、新規・更新・変更なし・削除候補(保存済みだがエクスポートに含まれなかったもの)を数える。**更新か変更なしかは、raw と写真の情報の集合の両方から作ったハッシュで判定する**(コメントは同じでも写真だけが削除された場合を「更新」として扱うため)。

**削除候補は、次の条件をすべて満たす場合だけ、反映を選べるようにする**(既定はオフ)。満たさない場合は件数と理由だけを表示し、削除は行わない。

1. ZIP または展開済みのフォルダから読み込み、ファイルに欠けが無い。
2. 不正で保存できなかったレコードを含めて、すべてのレコードを「含まれていた」と判定できている。
3. エクスポートの期間が、保存済みのデータの期間を両端とも覆っている(古いエクスポートや一部だけのエクスポートを除くため)。
4. 削除候補の件数が、保存件数の5% と 20件の大きい方以下である(大量削除を防ぐため)。

削除しても、エクスポートを読み込み直せば元に戻せる。

### 9.2.5 保存(IMPT-03)

- 保存の開始時に `import_in_progress` の印を付け、完了時に外す。
- 一定件数(例: 2,000件)ずつ、1つのトランザクションで `checkins`・`search_index`・`photos` を保存する。新規と更新のチェックインだけを書き込み、変更なしのものは書き込まない。写真は、書き込んだチェックインの分を今回の集合で置き換える。
- 削除候補の反映を選んでいれば、最後に、削除候補のチェックインとその `search_index`・写真の情報を削除する。
- 完了時に、取り込み状況(最終取り込み日時、最新チェックインの日時、期間、件数、直近の取り込みの件数)を更新する。
- 途中でタブを閉じたり失敗したりした場合は、保存済みの分は残り(冪等なので害は無い)、印が残る。次に開いたとき、読み込み直すよう案内する。
- 保存の前に `navigator.storage.estimate()` で空き容量を確かめ、足りなければ止める。保存中に容量不足のエラーが起きたら、その旨を表示する。

### 9.2.6 エラー時の扱い(IMPT-04)

| 事象 | 表示・動作 |
|---|---|
| 必要なファイルが無い | 「エクスポートの ZIP を選んでください」と、ZIP の中身の見分け方を案内する |
| ファイルの欠け | 「エクスポートの一部のファイルが見つかりません」と表示する。取り込みはできるが、削除候補は反映できない |
| 複数のエクスポートが混ざっている | 「複数のエクスポートが含まれています。1つずつ選んでください」と表示し、止める |
| 形式が想定と違う | 「エクスポートの形式が変わった可能性があります」と表示し、取り込みを止める |
| 一部のレコードが不正 | 除外した件数を表示し、残りは取り込む |
| 大きさ・件数の上限超過 | 上限を超えた旨を表示し、止める |
| 保存領域の不足 | 空き容量の不足を表示し、止める(保存済みの分は残る) |
| 保存領域が使えない | IndexedDB を開けない場合は、その旨と対処(プライベートブラウズをやめる、ブラウザの設定でサイトデータを許可する)を表示する |
| 他のタブで取り込み・削除・移行の実行中 | 「別のタブで処理中です」と表示する |
| 取り込みが中断された | スマホで他のアプリに切り替えたなどでワーカーが止まった場合は、「中断しました。もう一度読み込んでください」と表示する |

### 9.2.7 鮮度の案内

- ヘッダーとデータ管理画面に、最新チェックインの日時と最終取り込み日時を表示する。
- 最終取り込みから30日以上たっている場合は、検索画面にエクスポートの再申請を促す控えめな案内を出す【提案】。

## 9.3 検索方式

### 9.3.1 検索式の仕様(利用者向け)【決定】

| 記法 | 意味 | 例 |
|---|---|---|
| `語 語` | AND(スペース区切り) | `一蘭 渋谷` |
| `A AND B` | AND | `一蘭 AND 渋谷` |
| `A OR B` | OR | `一蘭 OR 二郎` |
| `( )` | グループ化(入れ子可)。括弧の前後には空白を入れる | `替え玉 AND (一蘭 OR 二郎)` |
| `"…"` | 空白・記号・演算子を含む語をそのまま検索する | `"一蘭 渋谷"`、`"H&M"`、`"12:30"`、`"OR"` |

| 規則 | 内容 |
|---|---|
| 検索対象 | 店名・コメント(shout)・場所名・イベント名(F-22 の変更)。住所・カテゴリはエクスポートに含まれないため対象外。ヘルプと該当なし画面で明示する |
| 一致の仕方 | 各語は部分一致で、検索対象のどれかに含まれれば一致とする |
| 表記ゆれ | 全角/半角、大文字/小文字は区別しない(F-23)。ひらがなとカタカナは区別する |
| 演算子 | 大文字の AND / OR(全角の ＡＮＤ・ＯＲ も可)。**小文字の and / or はエラーにし**、大文字での入力か、語として検索する場合は引用符で囲むよう案内する(17章 D-5 で決定) |
| AND と OR の混在 | **同じ括弧の中で AND(スペースを含む)と OR を混ぜたらエラーにし**、括弧を付けた例を示す(17章 D-4 で決定)。liqe は AND と OR に優先順位を持たず左から順に結合するため、意図と違う検索を防ぐ |
| 括弧の空白 | 括弧が語に密着しているとエラーになる。空白を入れるよう案内する |
| 対応しない構文(F-26) | フィールド指定(`venue:一蘭`)、比較・範囲(`count:>5`、`[1 TO 5]`)、正規表現(`/…/`)、除外(`NOT A`、`-A`)、ワイルドカード(`*`、`?`)はエラーにする。部分一致なので `*` は不要である旨と、記号として検索する場合は引用符で囲むことを案内する |
| 記号 | `&`、`'`、`%`、`+`、`:`、`/`、`!` などを含む語は、引用符で囲まないと解釈できない。エラーの位置にある文字に応じて具体的な案内を出す |
| 上限 | 入力200文字、1語50文字、語数10、括弧の入れ子5段 |
| 空の検索式 | 全件を新しい順に表示する(閲覧モード) |
| 解釈の表示 | 実際に検索した条件を「解釈: 一蘭 OR (ラーメン AND 渋谷)」の形で表示する |

### 9.3.2 処理方式【決定】

画面で行うこと:

1. 長さを確認する(liqe は引用符なしの長い語で処理時間が急増するため、パースの前に制限する)。
2. 空白類(全角スペース・タブ・改行)を半角スペースに、全角括弧を半角に、全角・スマートの二重引用符を `"` に置き換える。入力全体には NFKC 正規化をかけない(`㈱` が `(株)` になり括弧と解釈されるなどの副作用があるため)。
3. liqe(3.8.7)でパースする。
4. 9.3.1 の規則で検証し、中間AST(`{type: 'and'|'or', children}` / `{type: 'term', value}`)に変換する。パース結果の中で語として現れた全角・小文字の演算子語は、NFKC 正規化して判定し、全角の大文字は演算子として扱い直し、小文字はエラーにする。同じ演算子の入れ子は平坦化し、同じ語の重複は除く。liqe のエラーは位置付きの日本語メッセージに変換する。
5. 中間AST を検索ワーカーに渡す。

検索ワーカーで行うこと:

6. 中間AST を再検証する(語数・深さ・語の長さ・未知の type)。
7. 各語を検索用テキストと同じ関数で正規化し、中間AST を照合用の関数の木に組み立てる。**文字列からコードを作って実行する方法(`eval`、`new Function`)は使わない**。
8. メモリ上の検索用データ(日時の降順に並べたもの)を順に照合し、該当したチェックインを数え、表示ページ分の ID を取り出す。
9. 表示ページ分のチェックインと写真の情報を IndexedDB から読み、画面に返す。

### 9.3.3 正規化と照合(F-21〜F-23)

- 検索用テキスト = 小文字化(NFKC(店名 + コメント(shout) + 場所名 + イベント名))。区切りには改行を使い、語が項目をまたいで一致しないようにする。取り込み時に作り、`search_index` に保存する。
- 検索語にも同じ関数をかけ、部分一致(文字列が含まれるか)で照合する。データと検索語に同じ JS の関数を使うので、正規化の結果がずれない。
- 正規化の関数を変えたときは、保存形式の版を上げ、移行処理で raw から検索用テキストを作り直す(9.1.3)。
- SQL を使わないため、LIKE の特殊文字のエスケープは不要になる。

### 9.3.4 性能(N-05)【暫定 S-6】

- 検索ワーカーは、起動時と取り込みの後に、`search_index`(ID・日時・検索用テキスト)だけを IndexedDB から読み込んでメモリに持つ。raw を含む `checkins` は全件読まず、表示ページ分だけを都度読む。
- 目標: 一般的なスマホで、5万件の検索(総件数を含む)が 300ms 以内、検索用データの準備が 3秒以内。PC では20万件でも同程度。
- 目標を満たさない場合の対策を用意しておく: `search_index` を一定件数ずつまとめた塊で保存して読み込みの回数を減らす、文字の組(2文字ずつ)の索引を作って候補を絞り込む、件数の多い端末では上限件数を下げる。

### 9.3.5 外部との関係(F-25)

検索はブラウザの中だけで行う。外部の API には接続しない。

## 9.4 詳細表示方式(F-33)

- 詳細は保存データだけで表示する。
- 写真の URL は、許可したパターンに一致する prefix と suffix(S-1 の実データで確定。例: prefix が `https://fastly.4sqi.net/img/` で始まり、suffix がファイル名の文字だけで構成される)から組み立てる。パターンは取り込み時に検証し、表示時にも再確認する。表示は `<img referrerpolicy="no-referrer" loading="lazy">` で行い、一覧のサムネイルは小さいサイズ、詳細は大きいサイズにする。非公開写真が URL だけで表示できるかは S-1 で確認する。
- 「Foursquare で店を見る」は、検証済みの venue ID から `https://foursquare.com/v/{venue_id}` を組み立てる。
- 店名・コメントなどは表示の前に制御文字と双方向制御文字を取り除く(5.5)。

## 9.5 削除・データ保持方式

| 処理 | 方式 | 要件 |
|---|---|---|
| データの削除 | 利用者の操作で、確認ダイアログの後に即時に削除する。猶予期間は設けない(17章 D-2 で決定)。手順は 4.2.4 のとおり: 取り込みと同じ排他ロックを取り(取り込み・移行の実行中は、終わるのを待つか中止を選ぶ)、自分のタブの接続(画面・両ワーカー)を閉じ、データベースごと削除する。他のタブには `versionchange` が届き、接続を閉じる | F-03, F-40 |
| 削除できなかった場合 | 他のタブが接続を閉じないなどで削除が保留になった場合は、「他のタブを閉じてください」と案内する | — |
| 削除で消えないもの | ブラウザの閲覧履歴(検索式を含む URL)と、写真の画像のキャッシュはアプリからは消せない。確認ダイアログとデータ管理画面で、共有の端末ではブラウザの履歴とキャッシュも削除するよう案内する | — |
| 自動の削除 | 本アプリは自動では削除しない。ブラウザ自身が消す場合はある(9.1.2) | — |

**プライバシーポリシーに記載する事項**:

- 取り込んだデータは、利用者の端末のブラウザの中だけに保存し、運営者のサーバーには送らないこと。運営者はデータを見られないこと
- 取り込むデータ(位置情報を含むチェックイン、写真の情報)と、読み込まないデータ
- 写真を表示するとき、Foursquare の画像 CDN に接続すること(IP アドレスなどが Foursquare に送られる)
- サイトの配信(Netlify)で、通常の Web アクセスの記録(IP アドレス、ページの URL の `#` より前の部分など)が残ること。検索語は送られないこと
- 検索式は URL の `#` 以降に入るため、ブラウザの閲覧履歴に残り、ブラウザの履歴の同期を使っている場合は同期先(Google・iCloud など)にも保存されることがあること(17章 D-10)
- データの削除では、ブラウザの閲覧履歴と画像のキャッシュは消えないこと
- 訪問者数の計測(Vercel Web Analytics。Cookie なし)は、トップ・このアプリについて・プライバシーポリシーの3ページだけで行い、検索・取り込み・データ管理では行わないこと。広告・Cookie は使わないこと
- 同じブラウザを使う人はデータを見られること、削除の方法
- 問い合わせ先

## 9.6 タブ間の調整(APP-02)

- 取り込み(分析の開始から保存の完了まで)、データの削除、保存形式の移行は、同じ名前の排他ロック(Web Locks)を取って行う。同時には1つしか実行できない。
- データベースへの接続は、画面・取り込みワーカー・検索ワーカーのどれでも、`versionchange` を受け取ったらすぐに閉じる。接続を閉じたタブは、メモリ上の検索用データを捨て、**自動では開き直さない**(開き直すと削除や移行を妨げるため)。画面には「データが削除されました」または「新しい版があります。再読み込みしてください」を表示する。
- 取り込みが終わったら BroadcastChannel で他のタブに知らせ、他のタブは検索用データを読み直す。
- bfcache から復帰したタブは、`pageshow` で起動時の確認をやり直す(9.1.4)。

## 9.7 エラーハンドリング方針

- 利用者には原因と対処を日本語で示し、技術的な詳細は出さない。
- 画面単位の予期しないエラーは Next.js の `error.tsx` で受け、再読み込みを案内する。
- 対応していないブラウザ(IndexedDB・Web Worker が使えない)では、その旨を表示する。
- メッセージの一覧は詳細設計書で定める。

## 9.8 ログ・監視方針

- 運営者にデータが届かないため、利用者の端末のエラーは収集しない(エラー収集サービスも使わない)。
- 不具合の報告は、利用者が画面に表示された「エラーの種類(コード)」を問い合わせで伝える方式にする。表示するコードには、チェックインの内容を含めない。
- 運営者が見られるのは Netlify の配信の記録とデプロイの状況だけである。
