## 9.1 認証・セッション方式

### 9.1.1 ログイン【暫定 S-2】

- **Google**: Server Action で `signInWithOAuth`(PKCE)を呼び、返った URL へリダイレクトする。戻り先の `/auth/callback` で、Cookie の検証値を使って転送元IP付き Auth クライアントでコードを交換し、得たセッションをユーザークライアントの setSession で httpOnly Cookie に保存する。
- **メール**: 4.2.2 のとおり。Turnstile の検証、レート制限、ログイン意図の Cookie、確認画面、ログイン後のアドレスの一致確認を行う。
- ログイン後は、初回なら `accounts` の行を作り(DB 関数)、4.2.1 の分岐で遷移する。アカウント削除の処理中ならサインアウトして「削除処理中」を表示する。
- 戻り先はアプリ内の固定パスに限る(戻り先を引数で受け取らない)。

### 9.1.2 Cookie 設計

| Cookie | 用途 | 属性 | 有効期間 |
|---|---|---|---|
| Supabase セッション | セッション維持 | httpOnly・Secure・SameSite=Lax・Path=/。可能なら Cookie 名に `__Host-` 接頭辞を付ける(詳細設計で確認) | Cookie 自体は @supabase/ssr により400日固定。セッションの有効性は Supabase の設定に従う |
| PKCE の検証値 | Google ログインのコード交換 | httpOnly・Secure・SameSite=Lax | ログイン完了まで |
| ログイン意図 | 転送されたメールリンクでのログイン防止(4.2.2) | 署名付き・httpOnly・Secure・SameSite=Lax。メールアドレスの HMAC と乱数を持つ | 15分 |

- ローカル(`http://localhost`)では `Secure` と `__Host-` を外す。
- Cookie を設定・更新する応答には `Cache-Control: private, no-store` を付ける。

### 9.1.3 セッションの更新【暫定 S-2・S-4】

- **リフレッシュは proxy.ts だけが行う**。アクセストークンの期限の120秒前を過ぎたら、トークンの署名を検証したうえで(期限以外の検証に失敗する Cookie ではリフレッシュしない)、転送元IP付き Auth クライアントで `refreshSession` を呼び、結果をユーザークライアントの setSession で Cookie に書き戻す。Route Handlers・Server Actions・画面はリフレッシュしない(二重のリフレッシュで利用者がサインアウトされるのを防ぐ)。
- 利用者の IP は Netlify の `x-nf-client-connection-ip` から取る(S-4 で確認)。リフレッシュの失敗が IP 単位で続く場合は、その IP からのリフレッシュを一定時間止める。
- 転送元IP付き Auth クライアントが使えない場合は、Supabase 側で token の上限を引き上げる。
- Netlify での proxy.ts の動作(実行形態、バンドル不具合の有無、Cookie の書き戻し、環境変数の参照)は S-4 で確認し、問題があれば非推奨の middleware.ts(Edge)に切り替える。

### 9.1.4 ログアウト

- ユーザークライアントの signOut(scope: local)で、この端末のセッションだけを終了し、本アプリの Cookie を個別に削除する(Set-Cookie で期限切れにする)。
- 応答に `Clear-Site-Data: "cache"` を付ける。認証が必要な画面は `Cache-Control: no-store` とし、ブラウザの戻る操作でキャッシュから表示された場合(`pageshow` の persisted)は再読み込みする。`Clear-Site-Data` の `"cookies"` は、同じドメインのサブドメインの Cookie まで消すため使わない。
- 「すべての端末からログアウト」は scope: global で全セッションを終了する。
- 発行済みのアクセストークンはサインアウト後も有効期限(既定1時間)まで有効だが、Cookie が消えるのでブラウザからは使われない。削除要求中のアカウントは、DB 関数と RLS がデータへのアクセスと書き込みを拒否する。

### 9.1.5 同意の確認

- 各画面(page)・各 Route Handler・各 Server Action の冒頭で、ログインと「現在の版への同意」を確認する共通関数を呼ぶ(レイアウトはクライアント側の画面遷移で再実行されないため、レイアウトだけに頼らない)。
- 取り込みの DB 関数でも、同意の版を確認する。
- マイページは、再同意が未済でも、ログアウトとデータ・アカウントの削除だけは行えるようにする。

## 9.2 取り込み方式

### 9.2.1 全体の流れ【決定】

1. 利用者が Foursquare にエクスポートを申請する(本アプリは手順を案内するだけ。IMPT-01)。
2. 届いた ZIP を利用者が選ぶ。ブラウザ(Web Worker)で ZIP の目次だけを読み、`checkins*.json` と `photos*.json` だけを展開する(写真の実ファイルを含む大きな ZIP でも、全体をメモリに読み込まない)。
3. ブラウザで形式とファイルの欠けを検証し、ID の重複を除き、写真をチェックインに対応付け、件数・期間を表示する。
4. 利用者が「取り込む」を押すと、取り込みを開始し、チェックインレコードを連番付きの塊に分けて順に送る。
5. サーバーは各レコードを検証して raw を組み立て直し、DB 関数で保存する。
6. 全件を送り終えたら完了処理を呼び、差分を集計する。削除候補は、安全条件を満たす場合だけ利用者に確認する。

### 9.2.2 ブラウザでの読み込み(IMPT-02)

- ZIP の展開には、ファイルの目次から必要なファイルだけを取り出せるライブラリを使い、Web Worker の中で処理する(画面が固まらないようにする)。
- ZIP を展開済みで選んだ場合に備え、`checkins*.json` と `photos*.json` を直接選ぶこともできるようにする。ただしこの場合は、ファイルの完全性を確かめられないため、削除候補は提示しない(9.2.4)。
- 読み込み時の検証: 必要なファイルがあるか、`checkins` の連番に欠番が無いか、各ファイルの `count` と `items` の件数が一致するか、各レコードに id(24桁の16進数)と createdAt があるか。
- 同じ ID のレコードが複数あれば1件にまとめる。総件数は、重複を除いた有効な ID の数として申告する。
- 送信の前に、明らかに不要な項目(他人を指す entities など)を除く。最終的な項目の選別はサーバーで行う(9.2.3)。
- **送信しないもの**: 友人一覧・支払い・端末・訪問履歴などのファイル、写真の実ファイル(pix/)。
- 端末の負荷: 保存件数の上限の20万件(JSON 数十MB)まで、S-5 で PC とスマホの処理時間・メモリを確認する【暫定 S-5】。

### 9.2.3 分割送信と保存(IMPT-03)

- **開始**: 開始の DB 関数は、利用者単位で排他したうえで、送信中・確認待ちの古い取り込みを cancelled にし、新しい取り込みを登録する。申告された総件数が保存件数の上限を超える場合は開始しない。開始時点の保存件数と期間を控える(9.2.4 の比較に使う)。
- **送信の単位**: 500件以下かつ1MB 以下。各塊に連番を付ける(Netlify の関数のリクエスト上限 6MB と、1リクエスト10秒以内の制約に収めるため)。
- **サーバー(Route Handler)での検証と組み立て直し**: 認証・同意を確認したうえで、各レコードを zod で検証する。**raw は、許可した項目(id、createdAt、type、visibility、private、shout、timeZoneOffset、venue の id・name・url、location の name・lat・lng、event の id・name、comments の count)だけで組み立て直す**。未知の項目は保存せず、項目名だけをログに記録する(形式変更の検知用)。値の範囲(日時、タイムゾーン、緯度経度)と文字列の長さを検証し、raw は1件2KB 以下とする。ID は正しいが内容が不正なレコードは保存せず、その ID を「含まれていた ID」として DB 関数に渡す。
- **DB 関数での保存**: 利用者単位で排他し、取り込みがその利用者の最新のもので送信中であること、同意済み・削除要求中でないこと、連番が未受領であること(受領済みなら前回の結果を返す)、保存件数の上限、レート制限を確かめる。そのうえでチェックインを upsert する。**内容(raw)が変わった行だけを更新し**、新規・更新・変更なしの件数を数える。写真は、そのチェックインの分を今回の集合で置き換え、写真枚数を数え直す。含まれていた ID を `import_seen` に記録し、受領したレコードの期間を取り込みに反映する。
- 同じエクスポートを何度送っても結果が変わらない(冪等)。途中で失敗した場合は、取り込みを最初からやり直せばよい。

### 9.2.4 完了処理と差分の確定(IMPT-04)

- 完了処理では、サーバーが数えた受領件数(`import_seen` の件数)が申告された総件数と一致することを確認する。一致しなければ取り込みを失敗にし、削除は行わない(保存済みの行はそのまま)。
- 新規・更新・変更なしの件数と、「保存済みだが今回の取り込みに含まれなかった」件数(削除候補)を集計する。
- **削除候補は、次の条件をすべて満たす場合だけ利用者に提示する**。満たさない場合は削除せずに完了にし、必要ならエクスポート全体を選び直すよう案内する。
  1. ZIP から読み込み、ファイルに欠けが無い(`source_complete`)。
  2. 受領件数が申告件数と一致し、不正で保存できなかったレコードを含めて全件が「含まれていた」と判定できている。
  3. エクスポートの期間(サーバーが算出)が、開始時点の保存データの期間を両端とも覆っている(古いエクスポートや一部だけのエクスポートを除くため)。
  4. 削除候補の件数が、保存件数の5% と 20件の大きい方以下である(大量削除を防ぐため。上限値は `app_settings`)。
- 利用者が「削除する」を選んだら、DB 関数が同じトランザクションで、その取り込みが利用者の最新のもので確認待ちであること、削除候補を数え直して件数が変わっていないことを確かめてから削除し、完了にする。条件を満たさなければ何もしない。
- 「残しておく」を選んだら、削除せずに完了にする。確認待ちのまま24時間たった取り込みは、BATCH-01 が削除せずに完了にする。
- 完了した時点で、`last_imported_at` と `latest_checkin_at` を更新し、`import_seen` と `import_chunks` を削除する。

### 9.2.5 エラー時の扱い(IMPT-05)

| 事象 | 表示・動作 |
|---|---|
| 必要なファイルが無い | 「エクスポートの ZIP を選んでください」と、ZIP の中身の見分け方を案内する |
| ファイルの欠け | 「エクスポートの一部のファイルが見つかりません」と表示する。取り込みはできるが、削除候補は提示しない |
| 形式が想定と違う | 「エクスポートの形式が変わった可能性があります」と表示し、取り込みを止める(運営者がログで把握できるよう、ファイル名と項目名だけを記録する) |
| 一部のレコードが不正 | 除外した件数を表示し、残りは取り込む |
| 送信の失敗(通信・タイムアウト) | 同じ連番の塊を最大3回まで再送し(サーバーは重複を無視する)、だめなら「やり直す」ボタンを表示する |
| 上限超過(件数・頻度) | 上限に達した旨と、時間をおいて再試行するよう案内する |
| 削除処理中 | 「データの削除を処理しています」と表示し、取り込みを受け付けない |

### 9.2.6 鮮度の案内

- ヘッダーとマイページに、最新チェックインの日時と最終取り込み日時を表示する。
- 最終取り込みから30日以上たっている場合は、検索画面にエクスポートの再申請を促す控えめな案内を出す【提案】。

## 9.3 検索方式

### 9.3.1 検索式の仕様(利用者向け)

| 記法 | 意味 | 例 |
|---|---|---|
| `語 語` | AND(スペース区切り) | `一蘭 渋谷` |
| `A AND B` | AND | `一蘭 AND 渋谷` |
| `A OR B` | OR | `一蘭 OR 二郎` |
| `( )` | グループ化(入れ子可)。括弧の前後には空白を入れる | `替え玉 AND (一蘭 OR 二郎)` |
| `"…"` | 空白・記号・演算子を含む語をそのまま検索する | `"一蘭 渋谷"`、`"H&M"`、`"12:30"`、`"OR"` |

| 規則 | 内容 |
|---|---|
| 検索対象 | 店名・コメント(shout)・場所名・イベント名(F-22 の変更)。住所・カテゴリはエクスポートに含まれないため対象外。ヘルプと該当なし画面で明示する |
| 一致の仕方 | 各語は部分一致で、検索対象のどれかに含まれれば一致とする |
| 表記ゆれ | 全角/半角、大文字/小文字は区別しない(F-23)。ひらがなとカタカナは区別する |
| 演算子【提案 D-5】 | 大文字の AND / OR(全角の ＡＮＤ・ＯＲ も可)。小文字の and / or はエラーにし、大文字での入力か、語として検索する場合は引用符で囲むよう案内する |
| AND と OR の混在【提案 D-4】 | 同じ括弧の中で AND(スペースを含む)と OR を混ぜることはできない。エラーにして括弧を付けた例を示す。liqe は AND と OR に優先順位を持たず左から順に結合するため、意図と違う検索を防ぐ |
| 括弧の空白 | 括弧が語に密着しているとエラーになる。空白を入れるよう案内する |
| 対応しない構文(F-26) | フィールド指定(`venue:一蘭`)、比較・範囲(`count:>5`、`[1 TO 5]`)、正規表現(`/…/`)、除外(`NOT A`、`-A`)、ワイルドカード(`*`、`?`)はエラーにする。部分一致なので `*` は不要である旨と、記号として検索する場合は引用符で囲むことを案内する |
| 記号 | `&`、`'`、`%`、`+`、`:`、`/`、`!` などを含む語は、引用符で囲まないと解釈できない。エラーの位置にある文字に応じて具体的な案内を出す |
| 上限 | 入力200文字、1語50文字、語数10、括弧の入れ子5段 |
| 空の検索式 | 全件を新しい順に表示する(閲覧モード) |
| 解釈の表示 | 実際に検索した条件を「解釈: 一蘭 OR (ラーメン AND 渋谷)」の形で表示する |

### 9.3.2 処理方式【決定】

1. 長さを確認する(liqe は引用符なしの長い語で処理時間が急増するため、パースの前に制限する)。
2. 空白類(全角スペース・タブ・改行)を半角スペースに、全角括弧を半角に、全角・スマートの二重引用符を `"` に置き換える。入力全体には NFKC 正規化をかけない(`㈱` が `(株)` になり括弧と解釈されるなどの副作用があるため)。
3. liqe(3.8.7)でパースする。
4. 9.3.1 の規則で検証し、中間AST(`{type: 'and'|'or', children}` / `{type: 'term', value}`)に変換する。パース結果の中で語として現れた全角・小文字の演算子語は、NFKC 正規化して判定し、全角の大文字は演算子として扱い直し、小文字はエラーにする。同じ演算子の入れ子は平坦化し、同じ語の重複は除く。liqe のエラーは位置付きの日本語メッセージに変換する。
5. DB 関数(RPC)をユーザーの JWT で呼ぶ(POST)。
6. DB 関数の中で、次の順に処理する。
   - 引数の検証: 件数は 20 / 50 / 100 のいずれか、開始位置は上限(20万)以下、中間AST の大きさは 8KB 以下。
   - レート制限の判定。
   - 中間AST の再検証: 語数16、1語100文字、深さ8、子要素の数の上限、未知の type の拒否、制御文字の拒否。
   - 語の正規化(`search_text` と同じ関数で NFKC + 小文字化)と、LIKE の特殊文字のエスケープ(必ず正規化の後)。
   - 固定の部品から WHERE 句を組み立て、語は配列として `EXECUTE … USING` でバインドする(N-10)。
7. 総件数と表示ページ分のチェックインを返す。

- DB 関数は中間AST(構造化データ)だけを受け取り、SQL の断片は受け取らない。PostgREST を直接呼ばれても任意の SQL は実行されない。
- 検索関数は呼び出し元の権限で実行し(RLS 適用)、WHERE に `user_id = (select auth.uid())` を明記する。`search_path` は空に固定し、`statement_timeout`(3秒)を関数に付ける。

### 9.3.3 正規化と照合(F-21〜F-23)

- `search_text` = lower(NFKC(店名 + コメント(shout) + 場所名 + イベント名))を STORED の生成列で持つ。
- 照合は LIKE を使う(要件変更一覧 F-21)。両辺とも NFKC 正規化と小文字化を済ませているので、大文字小文字を区別しない点は ILIKE と同じで、ILIKE より 2.5〜6.5倍速い(PGlite での計測、条件による)。
- NFKC は全角の `％`・`＿`・`＼` を LIKE の特殊文字に変えるため、エスケープは正規化の後に DB の中で行う。アプリ側で正規化・エスケープした値を比較には使わない。

### 9.3.4 性能(N-05)【暫定 S-6】

- インデックス: (user_id, created_at 降順, id 降順)。全文用のインデックス(pg_trgm など)は作らない(1〜2文字の日本語の語では効果が無く、利用者単位の検索では使われないため)。
- raw は許可した項目だけで組み立て直して2KB 以下にしており、通常は数百バイトなので、checkins に持つ(API 方式で検討した別テーブル化は行わない)。
- PGlite での参考値は、1利用者5万件で総件数を含む検索が 200〜300ms。ネイティブの PostgreSQL では数十ms程度と推測する(未計測)。
- S-6 で目標(サーバー処理 p95 500ms 以内)を満たさない場合の対策を、効果の大きい順に用意しておく: 総件数を1ページ目だけ計算して保持する、検索関数を所有者権限にし関数の中で利用者と削除要求の状態を確かめたうえで明示的な利用者条件で絞る、PGroonga の導入。

### 9.3.5 外部 API との関係(F-25)

検索は DB だけを参照する。本アプリは外部の検索 API を使わない。

## 9.4 詳細表示方式(F-33)

- 詳細画面は保存データだけで表示し、副作用を持たない。
- 写真の URL は、許可したパターンに一致する prefix と suffix(S-1 の実データで確定。例: prefix が `https://fastly.4sqi.net/img/` で始まり、suffix がファイル名の文字だけで構成される)から組み立てる。パターンは取り込み時と DB の制約の両方で検証する。表示は `<img referrerpolicy="no-referrer">` で行い、一覧のサムネイルは小さいサイズ、詳細は大きいサイズにする。画像の複製や Next.js の画像最適化は使わない。閲覧者の IP が Foursquare の画像 CDN に送られることをプライバシーポリシーに書く。非公開写真が URL だけで表示できるかは S-1 で確認する。
- 「Foursquare で店を見る」は、検証済みの venue ID から `https://foursquare.com/v/{venue_id}` を組み立てる。

## 9.5 削除・データ保持方式

| 処理 | 方式 | 要件 |
|---|---|---|
| データの削除 | `getUser()` でセッションを確認し、DB 関数で削除要求(scope: data)を記録する。同時に、送信中・確認待ちの取り込みを中止する。記録した時点で RLS によりデータは見えなくなり、取り込みは拒否される。物理削除は BATCH-01 が行い、完了したら、記録時と同じ要求(日時と範囲が一致する)の場合だけ要求を消す | F-03, F-40 |
| アカウントの削除 | データの削除と同じく要求(scope: account)を記録し、全セッションを終了する。BATCH-01 がデータを物理削除した後、Supabase のユーザー自体を削除する(7.3)。処理中にログインした場合は、サインアウトして「削除処理中」を表示する | F-03, F-40 |
| 削除の所要時間 | 通常は要求から1時間以内に物理削除を完了する。BATCH-01 は10分ごとに実行し、1回の実行の中で対象が無くなるまで(最大5分)繰り返す。ロック待ちの上限を設け、取り込みの処理と長く競合しないようにする | F-40, F-42 |
| 初回の同意を拒否 | 何も保存していないため、管理クライアントでアカウントを即時に削除してトップに戻る | CONS-01 |
| 再同意を拒否 | データは削除せず、マイページ(ログアウト・データの削除・アカウントの削除だけができる)に移る | CONS-01 |
| 同意待ちの放置 | 初回の同意をしないまま7日たち、データが0件のアカウントは削除する(BATCH-01)【提案】 | — |
| 未確認のメールアカウント | メールでのログインを始めたまま確認しなかった(メールアドレス未確認の)ユーザーは、24時間後に削除する(BATCH-01) | N-11 |
| 放棄された取り込み | 24時間以上「送信中」のままの取り込みは失敗に、「確認待ち」のままの取り込みは削除せずに完了にする(保存済みの行はそのまま)。取り込みの記録は90日で削除する | F-42 |
| 長期間使われないアカウント | MVP では自動削除しない。扱いはプライバシーポリシーに書く(17章 D-6) | — |

BATCH-01 は条件で対象を選ぶ冪等な処理にし、途中で止まっても次回の実行で続きを処理できるようにする。バッチごとに確定するため、SET 句を付けないプロシージャで実装し、参照はすべてスキーマ修飾する。実行結果(cron の実行履歴)を監視し、古い履歴は削除する。

**プライバシーポリシーと利用同意に記載する事項(必須)**:

- 取り込むデータ(位置情報を含むチェックイン、写真の情報)と、取り込まないデータ
- 利用目的(本人の検索のみ)と、第三者に提供しないこと
- 保存場所(Supabase・Netlify のリージョン)
- 委託先(Supabase、Netlify、メール送信サービス、Cloudflare、Google)と、各社が米国法人であること。越境移転の扱い(個人情報保護法)は公開前に整理する
- 保持期間と削除方法、バックアップに残る期間
- ログインに使うメールアドレスと、Google のプロフィール(名前・アイコン。Supabase のユーザー情報とセッションに含まれる)の扱い
- レート制限・監査ログのために IP アドレスを扱うこと(レート制限では仮名化して保存すること)
- 写真を Foursquare の画像 CDN から読み込むこと
- 検索語がサーバーのアクセスログに残りうること
- 問い合わせ先

メール送信サービスのログの保持期間は、設定できる最短にする。

## 9.6 レート制限方式(N-03, N-12)

利用者単位の制限は Postgres の固定ウィンドウカウンタで実装する(P-3)。判定は private スキーマの所有者権限の関数で行い、public の薄い関数から呼ぶ。利用者単位のキーは関数の中で `auth.uid()` から作る。IP アドレスとメールアドレスは HMAC で仮名化してキーにする。

| 対象 | キー | 上限(初期値)【提案】 | 超過時の動作 |
|---|---|---|---|
| 検索(N-03) | ユーザー | 60回/分 | 「検索回数が多すぎます。少し待ってから再度お試しください」 |
| 取り込みの送信 | ユーザー | 120回/分。取り込みの開始は1日20回 | 待ってから再試行させる |
| ログインのメール送信 | IP(IPv6 は /64 単位)とメールアドレス | IP は 10回/10分(携帯回線などで多くの人が同じ IP を共有する場合を考慮)、アドレスは 3回/10分 | 時間をおいて再試行するよう案内する |
| ログインの確認(リンク・コード) | メールアドレスと IP | アドレスごとに失敗5回で、そのコードを無効扱いにして再送を求める。IP は 30回/10分 | 同上 |
| リフレッシュの失敗 | IP | 失敗が続いたら一定時間止める(9.1.3) | 再ログインを求める |

| 上限(N-12) | 値(初期値)【提案】 |
|---|---|
| 1利用者の保存件数 | 20万件 |
| 1回の送信 | 500件以下・1MB 以下 |
| raw の大きさ | 1件2KB 以下 |

- 検索のレート制限は DB の検索関数の中で判定するので、PostgREST を直接呼ばれても回避できない。判定は書き込みを伴うため、RPC は POST で呼ぶ。
- メールのリンクの確認は、トークンを当てるのが難しくてもアドレスで数えられないため、確認時にも CAPTCHA を求める。全体の確認失敗の数が急増したらログで把握できるようにする。
- 未認証の入口(ログイン)は、CAPTCHA と Netlify のレート制限ルール(netlify.toml、IP + ドメイン単位)を一次防御にし、DB のカウンタを二次防御にする。Next.js のルートに Netlify のルールが効くかは S-4 で確認する【暫定 S-4】。
- IP アドレスは Netlify の `x-nf-client-connection-ip` ヘッダから取得する(`x-forwarded-for` の左端は偽装されうるため使わない。S-4 で確認)。
- カウンタは古いウィンドウの行を定期的に削除する(BATCH-01)。DB 全体の容量を監視する。

## 9.7 エラーハンドリング方針

- 利用者には原因と対処を日本語で示し、技術的な詳細は出さない。外部から返ったエラー文言(OAuth の error_description など)はそのまま表示せず、固定の文言に変換する。
- 画面単位のエラーは Next.js の `error.tsx` / `not-found.tsx` で受ける。
- サーバーでは例外をエラー種別(入力エラー、認証エラー、取り込みの形式エラー、レート制限、システムエラー)に分類してログに出す。
- コード・メッセージの一覧は詳細設計書で定める。

## 9.8 ログ・監視方針

- Netlify Functions のログと Supabase のログ(Postgres / Auth / API)を使う。
- アプリのログは JSON 形式(時刻、レベル、イベント名、内部ユーザーID、所要時間、エラー種別、件数)で出力する。
- **ログに出さないもの**: Supabase のアクセストークン・リフレッシュトークン・ワンタイムトークン・コード・認可コード、Cookie、メールアドレス、IP アドレス(必要な場合は仮名化)、チェックインの内容(店名・コメントなど)、検索語の本文。キー名で自動的に伏せるロガーを使う。形式エラーの調査用には、ファイル名と項目名の一覧だけを記録する。
- 検索語は URL(`/search?q=`)に入るため、Netlify のアクセスログに残りうる。メールのリンクの token_hash も URL に入るため、確認画面で URL から消し、`Referrer-Policy: no-referrer` を付ける。これらはプライバシーポリシーに記載する。Postgres のログ設定(SQL 文やパラメータを記録しない設定)を確認する。
- 運営者が注意する事象: 取り込みの形式エラーの急増(エクスポートの形式変更の兆候)、ログインのメール送信・確認失敗の急増(悪用の兆候)、pg_cron の失敗、DB 容量と Netlify・Supabase の使用量の急増。MVP ではログの定期確認で運用し、通知の自動化は将来検討とする。
