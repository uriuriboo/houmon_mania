## 7.1 取り込むエクスポートの形式【暫定 S-1】

Foursquare はエクスポートの形式を公式に文書化していない。以下は2019〜2026年の実例から組み立てた想定で、S-1 で実物を確認して確定する。

| ファイル | 想定 | 使い方 |
|---|---|---|
| `checkins*.json`(`checkins1.json`、`checkins2.json`… または `checkins.json`) | `{"count": N, "items": [チェックインレコード…]}`。1000件ずつ分割 | すべて読み込む。連番の欠番と、各ファイルの件数を確認する |
| `photos*.json`(`photos.json` または `photos1.json`…) | 写真の情報(id, createdAt, prefix, suffix, width, height, visibility, fullUrl, relatedItemUrl) | relatedItemUrl でチェックインに対応付ける |
| その他(users, visits, unconfirmed_visits, comments, tips, lists, venueRatings, paymentProfiles, uniqueDevices, pix/ など) | — | **読み込まない・送信しない** |
| `*.csv` | JSON と同じ内容 | 使わない(JSON を優先) |

チェックインレコードの想定(2024-11 の実例。ID はマスク):

```json
{"id":"673583d9xxxxxxxxxxxx5c32","createdAt":"2024-11-14 05:00:09.000000","type":"checkin",
 "visibility":"closeFriends","entities":[],"shout":"Kareoke time!","timeZoneOffset":-300,
 "venue":{"id":"52854129xxxxxxxxxxxxff56","name":"The Brew Inn","url":"https://foursquare.com/v/..."},
 "comments":{"count":0}}
```

取り込み処理の前提:

- ファイル名は前方一致とワイルドカードで探す(`checkins*.json`、`photos*.json`)。
- createdAt は文字列(UTC)と UNIX 秒の整数の両方を受け付ける。
- venue・visibility・shout が無いレコードを許容し、venue の代わりに location を持つレコードや、event を持つレコードも扱う。
- 既知でない形式(想定するファイルが無い、レコードに id や createdAt が無いものが多い)の場合は取り込みを止め、形式が変わった可能性を案内する。

## 7.2 認証(Supabase Auth)

| 項目 | 内容 |
|---|---|
| プロバイダ | Google(OAuth)、Email(ワンタイムリンクとコード) |
| フロー | Google は PKCE。メールのリンクは token_hash を使う確認画面方式(4.2.2)。ログインの開始・完了はすべてサーバー側で行う |
| サインアップ | 公開(Google またはメールで誰でも始められる)。手動の ID リンクとメールアドレスの変更は無効にする |
| CAPTCHA | **Cloudflare Turnstile をアプリ側(Server Action)で検証する**(シークレットは Next.js の環境変数)。ホスト名・アクション名の一致と、トークンの再利用の拒否を確かめる。Supabase Auth は secret key での呼び出しでは CAPTCHA を検証しないため、Supabase 側の CAPTCHA 設定は、万一 publishable key で直接呼ばれた場合の保険として有効のままにする |
| 同じメールアドレス | Google とメールで同じアドレスを使った場合は、Supabase の自動リンクで同じユーザーになる(未確認の ID は自動リンクで除かれる) |
| メールの文面 | 外部 SMTP(例: Resend)で送る。**「Confirm signup」と「Magic Link」の両方のテンプレート**に、`/auth/confirm?token_hash={{ .TokenHash }}` へのリンクとコード(`{{ .Token }}`)を載せる(未登録のアドレスには Confirm signup が送られるため)。確認時の type はサーバーで固定する |
| コード | 有効期限は10分以下。桁数は設定値(推奨8桁)に従い、画面は設定値から桁数を決める |
| リダイレクト URL | 本番とローカル(`http://localhost:3000`)を Supabase Auth の許可リストに登録する。Google Cloud の OAuth クライアントは環境ごとに分ける |
| JWT 署名鍵 | 非対称(ES256) |
| レート制限 | Supabase Auth の IP 単位の制限(メール送信・確認 30回/5分、token 150回/5分など)は、サーバーから呼ぶとサーバーの IP に集中する。**メール送信・確認・コード交換・リフレッシュは、すべて転送元IP付き Auth クライアントで呼び**、利用者の IP ごとに数えられるようにする【暫定 S-2】。あわせて、アプリ側でも IP・アドレス単位の制限をかける(9.6) |
| 監査ログ | Supabase Auth の監査ログ(メールアドレスと IP を含む)の保持期間を決め、古いものを削除する(DB への記録を止められる場合は止める)【暫定 S-3】 |
| セッション | 最長期間と無操作タイムアウトは、プランで使えれば設定する(詳細設計で値を決める) |

ローカルの config.toml も同じ設定にそろえる(メールはローカルの Mailpit で受け取る)。

## 7.3 Supabase

| インタフェース | 用途 | 使用クライアント |
|---|---|---|
| Auth API | Google ログインの開始(signInWithOAuth)、サインアウト、ユーザー確認(getUser) | ユーザー |
| Auth API | メール送信(signInWithOtp)、確認(verifyOtp)、コード交換、リフレッシュ | 転送元IP付き Auth |
| Auth Admin API | 初回同意を拒否したアカウントの即時削除、全セッションの終了 | 管理 |
| PostgREST | テーブル参照、RPC(POST で呼ぶ) | ユーザー |

アカウント削除時の auth.users の削除は、BATCH-01(pg_cron)が SQL で行う。SQL から削除できない場合は、BATCH-01 から pg_net で Auth Admin API を呼ぶ(secret key は Vault に保管する)【暫定 S-3】。
