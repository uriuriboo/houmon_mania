## 12.1 環境

| 環境 | アプリ | DB / Auth | 用途 |
|---|---|---|---|
| ローカル | `next dev`(localhost:3000) | Supabase CLI のローカルスタック(Docker)。メールは Mailpit で受け取る | 開発 |
| 検証(任意)【提案】 | Netlify のブランチデプロイ(固定ドメイン、アクセス制限付き) | 開発用のクラウドプロジェクト | 結合確認 |
| 本番 | Netlify | Supabase クラウド(本番プロジェクト、関数と同じリージョン) | 公開 |

## 12.2 ローカル開発(L-01〜L-05)

| 要件 | 方式 |
|---|---|
| L-01 | Supabase CLI(npm の devDependency、バージョン固定)で `supabase start` を実行する。Docker 互換ランタイム(Docker Desktop / Podman / Rancher Desktop)が必要。現在の開発機は BIOS で仮想化を有効にする必要がある。導入できない間は、開発用の Supabase クラウドプロジェクトで代替する(L-01 からの一時的な逸脱) |
| L-02 | スキーマ・RLS・GRANT・関数・pg_cron の定義は、すべて `supabase/migrations` の SQL で管理する(手書き)。ローカルは `supabase db reset`、本番は `supabase db push` で適用する |
| L-03 | `.env.local`(Git の管理対象外)に、ローカルの URL・publishable key・secret key と、Next.js 側の秘密(Turnstile のシークレットのテスト用の値など)を置く。`.env.example` を雛形として管理する。Google OAuth のクライアント情報はローカルの config.toml が参照する `.env` に置く |
| L-04 | Google Cloud の OAuth クライアントを、ローカル用と本番用で分けて作り、それぞれのリダイレクト URL を登録する |
| L-05 | 個人情報をマスクしたエクスポート(S-1 で取得した実物を加工したもの)を fixture として用意し、取り込みのテストとシード投入に使う。ログイン済みの状態のテストは、アプリに経路を作らず、テスト用の補助処理がローカルの Supabase でセッションを作り、Playwright などでブラウザに Cookie を入れる方式にする |

ローカルの config.toml は本番と同じ Auth 設定にそろえる(Google・Email の有効化、メールの文面、コードの桁数と有効期限、署名鍵を ES256 に)。

## 12.3 環境変数(Next.js 側)

値はリポジトリに置かない。P-1 によりブラウザから Supabase を直接使わないため、`NEXT_PUBLIC_` 付きの変数は Turnstile のサイトキーだけにする。

| 変数 | 用途 | 秘密 |
|---|---|---|
| SUPABASE_URL | Supabase の URL | いいえ |
| SUPABASE_PUBLISHABLE_KEY | publishable key(ユーザークライアント用) | いいえ(ただしサーバーのみで使う) |
| SUPABASE_SECRET_KEY | secret key(管理クライアント・転送元IP付き Auth クライアント用。proxy.ts も使う) | はい |
| APP_ORIGIN | 自サイトのオリジン(Origin 検証とリダイレクトに使う) | いいえ |
| NEXT_PUBLIC_TURNSTILE_SITE_KEY | Turnstile のサイトキー(画面に埋め込む) | いいえ |
| TURNSTILE_SECRET_KEY | Turnstile の検証用シークレット | はい |
| COOKIE_SIGNING_SECRET | ログイン意図 Cookie の署名鍵 | はい |
| RATE_LIMIT_HMAC_SECRET | IP・メールアドレスを仮名化する HMAC 鍵 | はい |

上限値などの設定は DB の `app_settings` を正とする(環境変数には置かない)。Google OAuth のクライアントシークレットと SMTP の認証情報は Supabase の設定に置く。Netlify では、関数から使う変数は UI・CLI・API で設定し、秘密の変数は本番のデプロイコンテキストにだけ設定する。

## 12.4 デプロイ

- Git リポジトリと連携し、Netlify のクラウドでビルドする。main ブランチを本番にする。Windows のローカルビルドで報告されている proxy.ts の不具合がクラウドビルドで回避できるかは S-4 で確認する。
- Node のバージョンは `.nvmrc`(24)と `package.json` の engines でそろえる。
- DB マイグレーションの本番適用は `supabase db push` で行う(手動、または CI)。リリース順序は「DB マイグレーション → アプリのデプロイ」とし、マイグレーションは後方互換を保つ。
- クレジット制のプランでは本番デプロイ1回で15クレジットを消費するため、本番デプロイの回数を絞り、検証はブランチデプロイで行う。

## 12.5 テスト方針

| レベル | 対象 | ツール |
|---|---|---|
| 単体 | 検索式の解析・中間AST 変換、エクスポートの形式判定とレコードの検証・raw の組み立て直し(形の揺れ・欠損・未知の項目を含む)、写真の対応付け、ファイルの欠けの判定、ページ計算、日時表示、URL パラメータの正規化 | Vitest 5 |
| DB | RLS と権限(全テーブル・全関数)、検索関数(AND/OR/括弧、エスケープ、正規化、不正な引数・中間AST)、取り込み関数(上限、冪等性、連番の再送、他人の取り込みへの書き込み拒否、削除要求中の拒否)、削除候補の安全条件と確定時の競合、レート制限、削除バッチ | pgTAP(`supabase test db`) |
| 結合 | 取り込みの API(分割送信、完了処理、失敗とやり直し、古い取り込みの中止)、メールログインの確認画面とアドレスの一致確認 | Vitest |
| E2E | ログイン(テスト用セッション)→ 取り込み(マスク済み fixture)→ 検索 → 詳細 → ページ移動、ライト/ダークの表示 | Playwright |
| 実地 | 実際のエクスポートでの取り込み、Google・メールでのログイン | 手動(報告書 15.3 の手順) |
