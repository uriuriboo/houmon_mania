| 項目 | 内容 |

| 作成日 | 2026-10-16 |
| 対象文書 | `doc/1_requirements definition.md`(要件定義書) |

---

## 1. 変更の理由

技術調査で、Foursquare の Personalization API の利用ガイドライン(2026-02-12 更新)が、一般の開発者に対して ID 以外のデータのサーバー保存(キャッシュ)を禁止していることが分かった。チェックインを同期・保存して検索する当初の方式は、この規定と正面から衝突する(報告書 2.1)。

2026-10-16、ユーザー(要件オーナー)の判断で、データ取得方式を次のように変更した。

- 利用者が Foursquare 公式のデータエクスポート(「Download your data」)を自分で申請し、届いた ZIP を本アプリにアップロードする。
- 本アプリは Foursquare API を一切使わない(将来も使わない)。
- ログインは、Supabase Auth の Google ログインとメールのワンタイムリンクで行う(Swarm アカウントでのログインはやめる)。

## 2. 変更の影響(要約)

| 区分 | 影響 |
|---|---|
| 規約リスク | API のキャッシュ規定は「API が返したデータ」が対象のため、利用者自身が公式エクスポートで受け取ったデータには及ばない可能性が高い。ただし店名などは Foursquare の消費者規約上「個人的・非商用」の利用許諾であり、商用化する場合は法務確認が必要(報告書 15章) |
| 検索できる項目 | **エクスポートのチェックインには住所・市区町村・カテゴリが含まれない**ため、検索対象は「店名・コメント(shout)」(と、イベント名・場所名)になる。例: `カフェ` でスターバックスは見つからない、`渋谷` は店名に「渋谷」が入っている店だけ見つかる |
| 鮮度 | 自動同期は無くなる。新しいチェックインを反映するには、利用者が再申請し(通常2〜3日、最大7日)、ZIP を再アップロードする |
| 不要になるもの | Foursquare の開発者登録・OAuth・トークンの暗号化保管・同期処理・API のレート制限対応・Attribution 表示義務(API 規約上の義務。商標の扱いは引き続き必要) |
| 増えるもの | ZIP の取り込み機能(ブラウザ側での展開・検証・分割送信)、取り込みの差分確認、エクスポートの申請手順の案内 |

## 3. 要件ごとの変更

「変更後」の文言は提案であり、承認後に要件定義書へ反映する。

### 3.1 概要・スコープ

| 箇所 | 現行 | 変更後(提案) |
|---|---|---|
| 1章 目的 | Swarm アカウントを連携し、チェックイン履歴を店名・コメント等で検索 | 利用者が Foursquare 公式のデータエクスポートをアップロードし、チェックイン履歴を店名・コメントのキーワードで AND/OR 検索(入れ子構造含む)できる Web アプリ |
| 1章 想定利用者 | 各自が自分の Swarm アカウントを連携して使う | 各自が自分の Foursquare / Swarm のデータエクスポートをアップロードして使う。非商用で、本人のデータを本人が検索する用途に限る |
| 2.1 MVP に含むもの | Swarm アカウントでの実質的なログイン、チェックイン履歴の同期・永続化、詳細表示(オンデマンドで個別API取得)、連携解除時の猶予期間管理 | Google / メールのリンクによるログイン、エクスポート ZIP の取り込み・永続化、詳細表示(保存データのみ)、データとアカウントの削除 |
| 2.2 MVP に含まないもの | — | 追加: Foursquare API の利用(同期・詳細取得・住所やカテゴリの補完)、写真ファイルのアップロード |

### 3.2 認証(3.1 章「認証・アカウント連携」→「認証・アカウント」)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| F-01 | Swarm アカウントで実質的にログイン(Foursquare OAuth 後にサーバー側で Supabase ユーザー作成・セッション発行) | Supabase Auth により、Google アカウント、またはメールアドレス宛のワンタイムリンク(メールに記載のコードの入力も可)でログインできる。メールでのログインには CAPTCHA を課す。アプリ内での別途の会員登録は求めない |
| F-02 | access_token を暗号化して保存 | **削除**(トークンを扱わない) |
| F-03 | 連携解除操作。access_token を即座に無効化・削除 | **変更**: 利用者は自分の取り込みデータをすべて削除できる。また、アカウントを削除できる(データも含めて削除する) |
| F-04 | 連携状態をマイページで確認 | **変更**: マイページで、保存件数、保存済みの最新チェックインの日時、最終取り込み日時を確認できる |
| F-05 | ログアウトは Supabase セッションの終了のみ。保存済みトークンで再開 | **変更**: ログアウトは Supabase セッションの終了のみ。再ログインは Google またはメールのリンクで行う |

### 3.3 データ取得(3.2 章「データ同期」→「データ取り込み」)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| F-10 | 初回連携時に一覧APIで全履歴をバックフィル | 利用者は Foursquare 公式のデータエクスポート(ZIP)をアップロードして、全履歴を取り込める。ZIP の展開と必要なファイル(チェックインと写真の情報)の抽出はブラウザ側で行い、それ以外のファイル(友人一覧・支払い情報・端末情報・写真の実ファイルなど)は送信しない |
| F-11 | 同期中はプログレス状況を表示 | 取り込み中は進捗(読み込み・送信の件数)を表示する |
| F-12 | ログイン時に差分同期 | 新しいエクスポートを再度アップロードすると、差分(新規・変更・削除)を反映する。チェックインIDをキーに冪等に取り込む。削除の反映は、完全なエクスポートの取り込みが完了し、利用者が削除件数を確認した場合に限る |
| F-13 | レスポンス全体を raw JSONB として保存し、主要項目は個別列にも抽出 | エクスポートのチェックインレコード全体を raw JSONB として保存し、検索・表示に使う項目は個別列にも抽出する(保存しない項目を除く) |
| F-14 | 同期失敗時(レート制限・トークン失効)は再連携を促す | 取り込みに失敗した場合(形式の不一致、途中の通信失敗など)は、原因と対処を表示し、やり直せる(取り込みは冪等なので、最初からやり直しても重複しない) |
| F-15 | 一覧同期は一覧APIで完結、詳細APIはオンデマンドのみ | **削除**(API を使わない) |
| (新規) F-16 | — | エクスポートの申請手順(Swarm アプリ・Web の操作手順、届くまでの目安)を画面で案内する |

### 3.4 検索(3.3 章)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| F-20 | AND/OR・括弧の入れ子で検索 | 変更なし |
| F-21 | liqe でパースし、ILIKE の組み合わせに変換 | liqe でパースし、正規化済みの検索用列に対する LIKE の組み合わせに変換する(大文字小文字を区別しない点は同じ。ILIKE より速いため) |
| F-22 | 店名・shout・住所・カテゴリ名 | **店名・コメント(shout)・場所名(店の無いチェックイン)・イベント名**。住所とカテゴリはエクスポートに含まれないため対象外 |
| F-23〜F-26 | — | 変更なし(F-25 の「Foursquare API へ都度アクセスしない」は、API を使わないため自明になる) |

### 3.5 表示(3.4 章)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| F-30 | 日時・店名・カテゴリ・コメント・写真枚数 | 日時・店名・コメント・写真枚数・公開範囲(カテゴリはエクスポートに含まれないため除く) |
| F-31 | 件数表示、該当なし表示 | 変更なし |

### 3.6 データ保持・削除(3.5 章)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| F-40 | 連携解除後2週間の猶予期間を設けてソフトデリート | **変更**: データの削除・アカウントの削除は、操作後ただちに利用者から見えなくし、通常1時間以内に物理削除する。猶予期間は設けない(エクスポートを再アップロードすれば復元できるため) |
| F-41 | 猶予期間中の再連携でデータを復元 | **削除** |
| F-42 | 猶予期間経過後にバッチで物理削除 | **変更**: 削除要求されたデータ・アカウントの物理削除と、放棄された取り込み・古いレート制限カウンタなどの後始末を、定期バッチで行う |

### 3.7 ローカル開発環境(3.6 章)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| L-01 | Supabase CLI のローカルスタックを Docker Compose ベースで起動 | Supabase CLI のローカルスタックを起動できる(Docker 互換ランタイムが必要) |
| L-03 | ローカルの anon key・service role key・Foursquare Client ID/Secret | ローカルの publishable key・secret key と Next.js 側の秘密は `.env.local` に、Google OAuth のクライアント情報(ローカル用)はローカルの Supabase 設定(config.toml)が参照する `.env` に置き、本番の認証情報と混在させない |
| L-04 | Foursquare Developer Console にローカル用コールバック URL を登録 | Google Cloud の OAuth クライアントと Supabase Auth に、ローカル用のリダイレクト URL を本番用と別に登録する |
| L-05 | 実際の Swarm アカウントで OAuth、fixture でシード | 実際のエクスポート ZIP(個人情報をマスクしたもの)を fixture として用意し、取り込みとシード投入に使う。メールのリンクはローカルのメール確認ツール(Mailpit)で受け取る |
| L-02, L-06 | — | L-02 は変更なし。L-06(Vault の鍵)は、トークンを保存しないため削除 |

### 3.8 非機能要件(4章)

| ID | 現行 | 変更後(提案) |
|---|---|---|
| N-01 | 自分のデータのみ閲覧可能(RLS) | 変更なし |
| N-02 | access_token を Vault で暗号化しクライアントに送出しない | **削除**(トークンを扱わない) |
| N-03 | 公開検索エンドポイントにレート制限 | 変更なし。取り込み・ログイン(メール送信)にもレート制限をかける |
| N-04 | Foursquare API 呼び出しはサーバーサイドのみ | **削除** |
| N-05 | 数万件でも検索応答が数百 ms | 変更なし |
| N-06 | API 仕様変更時にも既存データは影響を受けない | エクスポートの形式が変わっても、取り込み済みのデータは影響を受けない(raw の保持による担保)。新しい形式には取り込み処理の改修で対応する |
| N-07 | 詳細取得エンドポイントのレート制限 | **削除**(取り込みのレート制限は N-03 に含める) |
| N-08 | OAuth の state による CSRF 対策 | Google ログインは Supabase Auth の PKCE フローで行う。状態を変える操作には CSRF 対策を行う |
| N-09 | 連携解除時の Foursquare 側トークン無効化 | **削除** |
| N-10 | 検索の SQL 生成はパラメータ化 | 変更なし |
| (新規) N-11 | — | 取り込みデータは本人以外が閲覧・利用できないこと。不要な個人情報(友人一覧、支払い・端末情報)はサーバーに送らない |
| (新規) N-12 | — | 1利用者あたりの保存件数・1回の送信サイズに上限を設ける |

### 3.9 データモデル(5章)・使用API(6章)・技術スタック(7章)

| 箇所 | 変更後(提案) |
|---|---|
| 5章 | `foursquare_accounts` を削除。`checkins` は複合主キー(user_id, id)とし、`location_name`、`event_name`、`visibility`、`photo_count` などを持つ(address・city・state・country・categories は持たない)。`deleted_at` は持たず、削除要求はアカウント単位で管理する。`checkin_photos`(写真情報)、`imports`(取り込みの記録)、`accounts`(利用同意・削除要求など)を追加。RLS の対象を「`checkins` と `foursquare_accounts`」から「利用者データを持つすべてのテーブル」に改める |
| 6章 | 「使用API」を削除し、「取り込むエクスポートの形式」(`checkins*.json`、`photos*.json` の想定項目)に置き換える |
| 7章 | 同期処理(Server Action)とシークレット管理(Vault)を削除。取り込み(ブラウザでの ZIP 展開 + Route Handler への分割送信)を追加。検索の「ILIKE」を「LIKE(正規化・小文字化済みの列)」に、ローカル開発の「Supabase CLI(Docker Compose)」を「Supabase CLI(Docker 互換ランタイム)」に改める。バージョン(Next.js 16.4.x、Node.js 24 LTS など)を明記 |

### 3.10 着手事項(実装前スパイク)

着手事項は、報告書 15.3 の実地検証 S-1〜S-6 に置き換える。検証1(Swarm ログイン)、検証2(差分同期)、検証3(API レスポンス)、検証4(revoke)、検証5(Foursquare OAuth のローカル動作)は不要になる。検証6(Supabase CLI)は Vault を除いて S-3 に統合する。検証7(liqe)は実施済み。

| ID | 内容 |
|---|---|
| S-1 | **実際の2026年版エクスポートを取得し、形式を確かめる(最優先)**。ファイル名、チェックインの項目、座標の有無、日本語の文字コード、写真の URL が表示できるか、ZIP のサイズ |
| S-2 | Supabase Auth の Google ログインとメールのリンク・コード(外部 SMTP、CAPTCHA、レート制限、転送元 IP の受け渡し) |
| S-3 | Supabase CLI のローカルスタック(pg_cron、権限、ロケール、auth.users の削除、監査ログ) |
| S-4 | Netlify へのデプロイ(関数のタイムアウト、proxy.ts、IP ヘッダ、レート制限ルール、アカウント種別) |
| S-5 | ブラウザでの ZIP の読み込みと取り込み時間(PC・スマホ、20万件まで) |
| S-6 | 検索の性能(1利用者3〜5万件) |

要件定義書の「着手事項は基本設計に入る前に完了させる」は、「実物の確認が必要な S-1〜S-6 は詳細設計と並行して行い、結果を詳細設計に反映する」に改める。
