# 要件定義書:Swarmチェックイン検索アプリ(MVP)

## 0. 本書の位置づけ

本書は要件定義のみを対象とする。以下は本書の範囲外とし、別文書(基本設計書・詳細設計書)で扱う:

- 画面遷移・UI具体仕様
- API・シーケンス図等の内部設計
- テーブルの物理設計確定(型・インデックス・制約の最終値)
- インフラ構成図・デプロイ手順の詳細

本書に含まれるテーブル定義・技術スタック等は「要件を満たすための想定」であり、基本設計時に変更されうる。

## 1. 概要

| 項目 | 内容 |
|---|---|
| 目的 | 各ユーザーが自分のSwarm(Foursquare)アカウントを連携し、チェックイン履歴を店名・コメント等のキーワードでAND/OR検索(入れ子構造含む)できるWebアプリ |
| 想定利用者 | 不特定多数への一般公開。各自が自分のSwarmアカウントを連携して使う |
| プラットフォーム | Webアプリ(レスポンシブ) |

## 2. スコープ

### 2.1 MVPに含むもの
- Swarmアカウントでの実質的なログイン
- チェックイン履歴の同期・永続化(一覧APIで完結)
- キーワードによるAND/OR検索(入れ子構造対応、liqeによるクエリパース)
- 検索結果一覧・詳細表示(詳細はオンデマンドで個別API取得)
- ユーザーごとのデータ分離
- 連携解除時のデータ猶予期間管理
- ローカル開発環境の整備

### 2.2 MVPに含まないもの(将来検討)
- 地図上での可視化
- 他ユーザーとのチェックイン共有・比較
- liqeのフィールド指定構文(`venue:xxx`等)・範囲検索などの高度な機能(パース結果に含まれても未対応入力としてエラーにする)
- モバイルネイティブアプリ

## 3. 機能要件

### 3.1 認証・アカウント連携

| ID | 要件 |
|---|---|
| F-01 | ユーザーはSwarmアカウントで実質的にログインできる(Foursquare OAuth2完了後、サーバー側でSupabaseユーザーの作成・セッション発行を行い、別途のアプリ内アカウント登録は求めない) |
| F-02 | 認可後のaccess_tokenは暗号化してサーバー側DBに保存する(クライアントには渡さない) |
| F-03 | 連携解除操作ができる。実行時はaccess_tokenを即座に無効化・削除する |
| F-04 | 連携状態をマイページで確認できる |
| F-05 | ログアウトはSupabaseセッションの終了のみを行う。Foursquare access_tokenは削除せず保持し、再ログイン時は保存済みトークンで即座にセッション再開できるようにする(Foursquare OAuthの再実行は不要) |

### 3.2 データ同期

| ID | 要件 |
|---|---|
| F-10 | 初回連携時、`GET /v2/users/self/checkins`(`v`必須・`limit`最大250・`offset`)で全履歴をバックフィル取得する |
| F-11 | 同期中はプログレス状況を表示する |
| F-12 | 2回目以降はログイン時に差分同期を行う。方式は着手事項での検証結果に基づき確定する(方式A: offset+既知ID到達で打ち切り / 方式B: 未文書化パラメータによる絞り込み) |
| F-13 | レスポンス全体をチェックインごとにraw JSONBとして保存する。検索・表示に使う主要項目は個別列としても抽出する |
| F-14 | 同期失敗時(レート制限・トークン失効)は再連携を促す表示を行う |
| F-15 | 一覧同期は一覧APIのレスポンスのみで完結させる。個別詳細APIは詳細表示時のオンデマンド取得にのみ使用する |

### 3.3 検索

| ID | 要件 |
|---|---|
| F-20 | ユーザーはキーワードとAND/OR演算子、括弧による入れ子構造(例:`A OR (B AND C)`)を用いて検索できる |
| F-21 | 検索クエリはliqeでパースしてASTを生成し、サーバー側でAND/OR/括弧に対応するSQLのWHERE句(ILIKEの組み合わせ)に変換する |
| F-22 | 検索対象:店名・shout(コメント)・住所・カテゴリ名(生成列`search_text`に集約) |
| F-23 | 全角/半角・大文字/小文字の表記ゆれを吸収する(NFKC正規化) |
| F-24 | 検索結果は日時降順、ページネーションあり |
| F-25 | 検索処理自体はFoursquare APIへ都度アクセスしない(事前同期済みデータのみを検索) |
| F-26 | liqeのフィールド指定・範囲検索等、AND/OR/括弧以外の構文が入力された場合はエラーメッセージを返す(未対応構文として明示的に弾く) |

### 3.4 表示

| ID | 要件 |
|---|---|
| F-30 | チェックイン一覧:日時・店名・カテゴリ・コメント・写真枚数 |
| F-31 | 検索結果件数の表示、該当なし時の表示 |
| F-33 | 検索結果一覧はDB保存データのみで表示する。1件クリックで詳細を開いた際は`GET /v2/checkins/{checkin_id}`を呼び最新情報を取得・raw上書き保存する |

### 3.5 データ保持・削除

| ID | 要件 |
|---|---|
| F-40 | 連携解除後、チェックインデータは即削除せず2週間の猶予期間を設けてソフトデリート状態で保持する |
| F-41 | 猶予期間中に再連携した場合はデータを復元する |
| F-42 | 猶予期間経過後、バッチ処理でチェックインデータを物理削除する |

### 3.6 ローカル開発環境

| ID | 要件 |
|---|---|
| L-01 | Supabase CLIによるローカルスタック(Postgres・Auth・Storage・Studio)をDocker Composeベースで起動できる |
| L-02 | DBスキーマ・RLSポリシーはSupabase CLIのマイグレーションファイルとして管理し、ローカル・本番間で同一の手順で適用できる |
| L-03 | ローカル環境用の`.env.local`(ローカルのanon key・service role key・Foursquare Client ID/Secret)を用意し、本番の認証情報と混在しない |
| L-04 | Foursquare Developer Consoleにローカルのコールバック用URLを本番用URLと別に登録する |
| L-05 | ローカル開発時は実際のSwarmアカウントでOAuthを通す。繰り返しテスト用に、取得済みJSONレスポンスのfixtureデータによるシード投入手段を用意する |
| L-06 | ローカルのVault/暗号化鍵は本番と別の鍵を使う |

## 4. 非機能要件

| ID | 要件 |
|---|---|
| N-01 | 各ユーザーは自分のチェックインデータのみ閲覧可能(RLSで強制) |
| N-02 | Foursquare access_tokenはSupabase Vault等で暗号化保存し、クライアントに一切送出しない |
| N-03 | 公開検索エンドポイントにレート制限をかける |
| N-04 | Foursquare API呼び出しはサーバーサイドからのみ行う。詳細表示時の個別API呼び出しはユーザー操作起点で許容する |
| N-05 | 数万件規模でも検索応答が数百ms程度に収まる |
| N-06 | API仕様変更・停止時にも既存データは影響を受けない(raw jsonb保持による担保) |
| N-07 | 詳細取得エンドポイントにもレート制限を設ける(連打防止) |
| N-08 | OAuth2認可フローでは`state`パラメータによるCSRF対策を実装する |
| N-09 | 可能であれば連携解除時にFoursquare側でもトークンを無効化する(revokeエンドポイントの有無を着手事項で確認) |
| N-10 | 検索クエリのASTからSQL生成する処理は、パラメータ化(prepared statement/USING句)によりSQLインジェクションを防止する |

## 5. データモデル(想定・基本設計で確定)

foursquare_accounts
  user_id (PK, FK -> auth.users)
  access_token (encrypted)
  fsq_user_id
  connected_at
  disconnected_at
  last_synced_at

checkins
  id (PK)
  user_id (FK)
  created_at
  tz_offset
  shout
  venue_id
  venue_name
  categories (text array)
  address
  city
  state
  country
  lat
  lng
  photo_count
  raw (jsonb, not null)
  search_text (generated column, normalized for search)
  deleted_at

RLS: `checkins` と `foursquare_accounts` はいずれも `auth.uid() = user_id` で制限。

## 6. 使用API(確認済み)

| エンドポイント | 用途 | 主なパラメータ |
|---|---|---|
| `GET /v2/users/self/checkins` | 一覧取得 | `v`必須・`limit`最大250・`offset` |
| `GET /v2/checkins/{checkin_id}` | 個別詳細取得(オンデマンド) | `v`必須 |

## 7. 技術スタック(想定・基本設計で確定)

| 領域 | 選定 |
|---|---|
| フロントエンド | Next.js + TypeScript |
| ホスティング | Netlify |
| DB/Auth | Supabase(Postgres + Auth + RLS) |
| 検索クエリパース | liqe(AND/OR/括弧のパース、フィールド構文等は未対応入力として弾く) |
| 検索 | PostgreSQL ILIKE + 生成列(NFKC正規化)、liqeのASTから再帰的にSQL生成 |
| 同期処理 | Server Action(初回) + ログイン時差分同期 |
| シークレット管理 | Supabase Vault |
| ローカル開発 | Supabase CLI(Docker Compose) |

## 着手事項(実装前スパイク)

以下は要件定義の各項目にある「検証してから確定」を先行して片付けるためのタスク一覧。基本設計に入る前に完了させる。

### 検証1: Swarmログインの技術検証
- Foursquare OAuth2(認可コード交換・access_token取得・fsq_user_id取得)の実装
- サーバー側(Service Role)でSupabaseユーザーを作成/紐付け、セッションを発行できるかの技術検証
- 結果次第でF-01の実装方式を確定

### 検証2: 差分同期 方式A/Bの比較検証
- 方式A(offset+既知ID打ち切り)の実装・動作確認
- 方式B(未文書化パラメータ)が実際に効くかの実クエリ検証
- 両方の実装コスト・信頼性を比較し、F-12の正式方式を確定

### 検証3: APIレスポンスの実地確認
- 一覧APIのフィールド欠損有無を実データで確認
- 個別詳細API(`/v2/checkins/{id}`)が一覧APIと比べてどのフィールドが追加/詳細化されているかを確認し、上書き保存する価値を判断

### 検証4: トークンrevokeエンドポイントの有無確認
- Foursquare OAuth2にaccess_tokenを明示的に無効化するエンドポイントが存在するか確認
- 存在すればF-03・N-09の実装に組み込む

### 検証5: Foursquare OAuthのローカル動作確認
- Developer Consoleでlocalhost用redirect_uriを登録できるか確認
- HTTPSが必須な場合、ローカル用トンネリング手段(ngrok/mkcert等)の選定

### 検証6: Supabase CLIローカルスタックの動作確認
- `supabase start`でのAuth Admin API・Vaultがローカルでも本番同様に動くか確認
- マイグレーション運用フロー(`supabase db diff` → `supabase db push`)の一連確認

### 検証7: liqeのAST→SQL変換の実装検証
- `A OR (B AND C)`程度の入れ子クエリをliqeでパースし、実際にAND/OR/括弧に対応するASTが得られるか確認
- 自作のSQL変換関数(再帰的にILIKE句へ展開)を試作し、想定通りのWHERE句が生成できるか確認
- フィールド指定・範囲検索等の未対応構文が入力された場合のエラーハンドリング方針を決める(F-26)
